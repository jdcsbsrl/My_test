# ERP 需求分析与测试计划

## 适用范围和边界

用户可以直接粘贴需求文字、图片或两者组合，无需填写提示词模板。默认完成需求分析、知识检索、测试范围设计、计划归档，并在同一轮对话中完整呈现计划内容和文件路径。

本 Skill 止于用户审阅的测试计划，不直接生成正式 15 字段 JSON 或 Excel。只有用户明确要求生成测试用例时，才进入 `docs/TRAE_TEST_WORKFLOW.md` 规定的 `case_generator_cli.py generate`、固定字段、AuditAgent 审核和 ExcelGenerator 链路；计划矩阵仅作为需求依据，不直接充当候选 JSON。

本 Skill 不执行 UI、API、回归或其他测试，不准备或修改测试数据，除非用户在当前任务中明确授权执行。不得写入或更新知识库，不输出账号密码、Token、Cookie 等凭证。

## 项目启动和规范

开始项目操作前确认根目录并读取 `AGENTS.md`。需求分析和计划使用时读取：

- `docs/TRAE_TEST_WORKFLOW.md`：覆盖维度、需求缺口状态和正式用例边界。
- `docs/KNOWLEDGE_BASE_RETRIEVER.md`：知识库 API、溯源和异常恢复规则。
- `docs/PROJECT_ARTIFACT_PLACEMENT.md`：计划文件位置、命名、修订和保留规则。

只有用户明确要求正式用例生成时才执行相应生成流程；只有用户明确要求测试执行时才读取 `docs/AUTO_TEST_WORKFLOW.md` 和其他相关执行规范。

## 需求和证据处理

1. 将每项明确需求标为 `R1`、`R2` 等。将原文、图片中可定位的区域和本次检索结果分别编为 `E1`、`E2` 等证据，并注明其支持的需求或场景。
2. 区分需求明确说明、知识库依据、当前实现观察、推断和待确认。当前实现不替代需求意图。用户当前明确提出的期望优先于历史资料；与知识库冲突时必须列明冲突和影响，不可静默选择。
3. 读取对话附件时使用当前可用的图片理解能力；本地图片使用当时可用的图片查看工具。只描述实际可见信息；无法辨认的字段、按钮和交互标为待确认，不猜测。
4. 需求 ID 可选。缺少模块、角色、数据或环境信息时，只有在其会改变计划范围或预期结果时才询问；可独立完成的部分继续分析，并一次汇总关键问题。环境通常仅在准备执行前需要确认。

## 知识库检索与溯源

必须通过 `KnowledgeRetriever` API 访问知识库，禁止按路径读取原始 JSON、分块文件或底层索引。按需使用 `retrieve()`、`search_business_rules()` 等精准查询；只有确需动态列出文件或索引时，才用 `get_index()` / `list_available_files()`，不得硬编码业务文件清单。

对每次有用的检索记录实际检索词、命中的文件/分块标识，以及结果实际提供的规则 ID、revision、`lifecycle_status` 和 `status_source`。不存在的元数据标为“未提供”，不自行编造。将 `deprecated`、`legacy`、`unknown` 显式标识；如返回 `superseded` 或 `draft`，同样标识并说明其历史/草稿性质，不作为现行依据静默使用。

检索无匹配时标注 `missing_knowledge`；有资料但不足以确定业务语义时标注 `needs_information`。这两个标签描述知识/依据状态，不等同于测试覆盖状态，也不冒称 AuditAgent 的审核结果。

注册表缺失、疑似过期，或发生知识库文件/注册表 `FileNotFoundError`、适用的 `OSError` 时，按检索指南调用 `refresh_registry()` 并对原查询重试一次；仍失败则报告检索异常，不改用原始文件路径读取，也不生成通用步骤冒充有依据的测试计划。

需求涉及菜单或路由归属时，使用正式知识库导航契约。截图中的动态计数徽标不是页面名称依据，已退役的本地导航样本不是来源。

## 测试范围和覆盖判定

逐项评估项目规定的七个基础维度：业务规则、业务对象、正常场景、异常场景、边界场景、回滚场景和排除项。角色权限、状态流转、幂等、数据持久性/一致性、接口和第三方失败、并发、性能、安全与审计、通知、导入导出、兼容性等作为补充维度，只有需求或风险触发时才展开。

分别报告两种状态，避免把“没有知识”误当成“没有测试覆盖”：

- **覆盖状态**：`covered`、`uncovered`、`not_applicable`、`needs_confirmation`。
- **依据状态**：`missing_knowledge`、`needs_information`，或注明当前依据来源。

每个不适用维度说明理由；每个覆盖缺口说明影响。依据不足时仍可交付计划，但受影响的场景和预期必须标为缺口/待确认，不得用通用步骤补齐。回归范围按项目风险规范选择；不得因缩小范围遗漏适用的 P0 场景。

优先级和用例等级沿用项目模板或 `RuleManager.get_field_value_rules()` 中实际配置的合法值。无法取得合法值时写“待确认”，不新增枚举。计划矩阵与正式 15 字段 Excel 是不同交付物，不把矩阵字段强行变成正式列。

## 计划结构和交付

按 `references/test-plan-template.md` 生成计划，至少包含范围摘要、需求/证据映射、覆盖矩阵、未确认事项及影响、排除项、回归范围和覆盖自查。步骤写清页面对象、动作和必要数据；预期应能观察和验证。未确认事项注明已知责任人及影响；责任人未知时写“待指定”。不使用无依据的覆盖率百分比。

将计划保存到 `workspace/YYYYMMDD/`，文件名为 `需求{需求ID}{需求名称}_测试计划.md`；无需求 ID 时省略 ID。文件名不得包含 Windows 禁用字符。保存前检查是否已存在同名文件；不覆盖历史计划，修订用 `_修订NN` 后缀递增。保存后调用 `AuditAgent.audit_test_plan()`；审核有错误时先修复并重新审核，通过后再交付。

保存后，在同一轮对话中展示完整计划正文和保存路径，不能只回复文件链接或“已保存”。用户审阅后如有修改，保存为新修订文件，并在对话中展示更新后的完整计划。

## 测试执行边界

若用户明确要求测试执行，确认当前任务的授权、执行范围和所需环境/角色信息。常规自动化仅限 `test`/`uat`；生产默认禁止，按项目专用只读流程处理获明确授权的生产专项。`--execute` 只是程序开关，不是授权。UI 自动化的浏览器、登录和会话按 `docs/AUTO_TEST_WORKFLOW.md`；不得未经允许切换浏览器或泄露认证信息。测试计划本身不启动浏览器、不运行测试、不创建或修改数据。
