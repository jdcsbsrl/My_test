# 需求测试计划模板

Skill 执行时用此结构输出。计划 Markdown 文件与对话回复保持内容一致。

## 摘要

- 需求 ID / 名称：已知时填写；未知或未提供时标注。
- 范围与主要风险：说明纳入内容及高影响场景。
- 证据状态：区分知识库无命中（`missing_knowledge`）和依据不足（`needs_information`）。
- 待确认事项：只列会影响范围、预期或执行准备的问题。

## 需求与场景矩阵

| 场景 ID | 需求 ID | 证据 ID | 覆盖维度 | 场景与优先级 | 账号/权限 | 页面入口 | 数据/状态 | 步骤（页面对象 + 动作 + 数据） | 可观察预期（页面/字段/状态/接口/数据） | 测试方式 / 自动化候选 | 覆盖状态 | 依据状态 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|

填写约定：

- 场景 ID 在本计划内稳定唯一，如 `S1`；需求 ID 如 `R1`；来源证据如 `E1`。不适用的来源明确标记。
- 覆盖维度先检查七个基础项：业务规则、业务对象、正常、异常、边界、回滚、排除项；补充维度须有需求或风险依据。
- 覆盖状态使用 `covered`、`uncovered`、`not_applicable`、`needs_confirmation`。`missing_knowledge` 和 `needs_information` 属于依据状态，不代表场景未覆盖。
- 优先级和用例等级仅使用项目配置中的值；配置无法确认时标“待确认”，不新增枚举。
- 步骤写明页面对象、动作和必要测试数据；预期写可观察结果。不要用“操作成功”“符合预期”代替具体断言。
- 图片、知识库、当前代码和用户补充资料使用不同证据 ID；知识库证据注明检索词和可用的文件/分块、规则 ID、revision、`lifecycle_status`、`status_source`。

## 覆盖自查

- 每项明确需求均映射到场景，或说明不适用理由。
- 七个基础覆盖维度逐项记录为已覆盖、不适用、未覆盖或待确认。
- 条件性维度说明触发理由；没有触发时不生造测试。
- 每个场景都有需求/证据依据，或明确标注缺口。
- 预期结果可观察；步骤可执行；未确认项注明影响及责任人（未知则写“待指定”）。
- 回归范围覆盖受影响共享能力；适用的 P0 场景没有因缩减范围而遗漏。
- 列出排除范围及理由，不给无依据的覆盖率百分比。

## 回归范围

说明受影响模块、共享能力、建议的回归级别及理由。若无法确认影响域，标记待确认，不宣称已覆盖。
