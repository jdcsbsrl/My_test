# 商品销量报表回归（1003420）

## 范围与入口

销售侧旧报表已合并到产品侧商品销量报表。旧页面对象和回归已退役；现有主回归为 `modules/auto_test/tests/test_sales_volume_regression.py`，角色回归为 `test_sales_volume_role_regression.py`，排序和导出顺序为 `test_sales_volume_sort_regression.py`。本地登记表中只读检索未发现旧脚本或旧名称的登记关联，历史测试产物保留。

仅在获得授权的 test/uat 环境执行。管理员非 slow 回归命令：

```powershell
$env:AUTO_TEST_AUTHORIZED='true'
$env:TEST_ENV='test'
$env:SALES_VOLUME_ROLE='admin'
pytest modules/auto_test/tests/test_sales_volume_regression.py modules/auto_test/tests/test_sales_volume_role_regression.py modules/auto_test/tests/test_sales_volume_sort_regression.py -m 'not slow'
```

CI 将商品销量报表分成三个有界并行泳道，最多同时运行 3 条：泳道 A 执行管理员，泳道 B 依次执行业务员和采购，泳道 C 依次执行组长/业务经理和业务助理。管理员仍运行完整主回归与 slow 回归；其类目订单数对账单独限时执行，对每个候选店铺的订单源做一次不带 SKU ID 过滤的完整扫描（最多 20 页），以免订单头按组合 SKU 父项存储时漏掉展开为子 SKU 的订单明细。命中多 SKU 同类目订单后再按类目 SKU 集合计数；页数上限或 15 分钟预算耗尽都明确失败为不完整，不接受部分数据通过。组合 SKU 样本检查作为单独 slow 阶段运行，按订单分页后逐页查询明细，找到样本即停止；单个查询最多 20 页，共享搜索预算 7 分钟。这样避免在普通筛选阶段执行 6 个月历史扫描和整批订单明细读取。每角色开始回归前会检查该角色可访问的报表接口；仅网络异常和 HTTP/应用层 5xx 在最多 10 分钟内重试，401 和其他非重试响应立即失败。每条泳道 job 最长 110 分钟；服务就绪失败停止整条泳道；其他阶段超时或标记不完整后只跳过当前角色余下阶段，继续同泳道下一个角色；普通断言失败继续后续检查并在最终结果中失败。阶段日志与 Allure 结果均作为泳道产物上传；失败或取消的 job 都进入失败日志收集。前置 job 按 Asia/Shanghai 时区生成唯一的 `SALES_VOLUME_AS_OF_DATE`，所有角色和 pytest 子进程共用该日期锚点；报表对账窗口取锚点前 30 个完整自然日，排除仍在变化的当天订单。每个角色切换后单独设置账号和 `SALES_VOLUME_ROLE`，每个 pytest 阶段使用不同的 `.runtime/cache/` 临时目录。角色可选 `admin`、`manager`、`sales`、`assistant`、`procurement`，必须与当前账号真实角色一致。采购没有店铺 Tab，店铺权限列表为空；仓库和国家筛选按采购账号可访问的数据范围查询。采购不参加双店筛选，但会单独验证不带店铺筛选的异步导出。不要在代码或报告中保存凭据。

为减少共享管理员账号的会话互相失效，使用管理员凭据的现有 UI job 先全部结束，再运行周报角色检查（该矩阵 `max-parallel: 1`）和周报管理员来源对账；三条商品销量泳道随后启动。泳道 B/C 不再登录管理员账号做采购数据对账或越权店铺检查，这些管理员交叉核对统一放在 `sales-volume-admin-crosschecks` job，在三条泳道结束后由一个 runner 依次执行。这样消除了商品销量泳道之间及旧 UI job 与商品销量泳道之间的管理员会话重叠；旧 UI job 内部仍按现有配置最多并行 2 个分片。其他不使用管理员账号的 CI job 仍可并行运行。

CI 使用 `ADMIN_USERNAME`/`ADMIN_PASSWORD`、`LEADER_USERNAME`/`LEADER_PASSWORD`、`SALES_USERNAME`/`SALES_PASSWORD`、`ASSISTANT_USERNAME`/`ASSISTANT_PASSWORD`、`PROCUREMENT_USERNAME`/`PROCUREMENT_PASSWORD` Secrets。各泳道保留每个角色、每个阶段的结果摘要和独立 Allure 结果；管理员交叉核对有单独的结果摘要和 Allure artifact。

报表查询遇到 HTTP 401 或应用层 `code=401` 时，测试立即失败，不自动重登或重试，并记录角色、接口、HTTP/应用状态码、会话年龄、登录次数、刷新次数和服务端 request ID；诊断中不记录密码或 token。导出任务列表是只读 GET，遇到网络异常或 5xx 最多重试 3 次（间隔递增）；401、其他客户端错误和“创建导出任务”请求均不重试，避免掩盖权限问题或重复创建任务。

订单源对账失败时，断言会附上共享日期窗口、店铺范围，以及差异 SKU 对应的逐订单状态、付款时间、店铺 ID 和明细数量，并立即用相同窗口重查订单源和报表。重查仍一致则判定为稳定的数据差异并失败；重查期间数值变化则标记为数据变化、测试不完整。这样可以区分报表口径差异与执行期间的数据变化；不得把滚动日期范围的汇总数当作固定预期值。

组合 SKU 样本检查按订单分页并对每页订单查询明细，命中后立即停止，不再先加载该窗口的全部订单和明细。当前窗口优先使用已验证有销量的店铺；找不到时，按该角色可见范围依次搜索最近六个自然月，使用 30 天时间块，每个窗口最多 20 页，共享 7 分钟预算。找到订单后按付款时间、订单号和组合 SKU 确定样本，再以付款分钟窗口重查订单源并对账。六个月仍找不到非作废组合订单时明确报告 `INCOMPLETE`；组合 SKU 定义总数不代表存在销售订单，不得把缺样本判为报表通过或报表功能缺陷。

每次 CI 自动执行角色权限、适用的筛选及来源对账，以及慢速排序和导出：管理员运行完整主回归；业务经理、业务员、业务助理运行多店异步导出；采购运行仓库/国家筛选、自身订单和库存接口核对，以及 SKU、发货仓库、国家、类目四个可见维度的采购异步导出。采购与管理员数据对账、业务经理/业务员/业务助理对未授权店铺的核对，在管理员交叉核对 job 中串行执行。后台导出任务需要运行中的任务服务，会在共享环境创建并保留任务。各角色执行的筛选范围仍是当前脚本中明确列出的子集；样本、接口权限、未匹配库存或后台服务不足均不能视为通过。三个泳道和管理员交叉核对 job 分别上传 Allure artifact，步骤摘要和日志按角色及阶段记录结果。

异步导出和排序导出属 slow：

```powershell
pytest modules/auto_test/tests/test_sales_volume_regression.py -m slow
pytest modules/auto_test/tests/test_sales_volume_sort_regression.py -m slow
```

异步测试使用 ERP 默认维度任务名前缀（`商品销量报表_{维度}`），由服务端追加时间戳；不传 `taskDesc`，提交前记录该名称下已有任务 ID，提交后通过新增任务 ID 跟踪状态，因此描述保持 ERP 默认值。任务保留；需任务服务正常运行。结果来自文件本身，前后源数据变化则报告验证不完整。下载产物放入 `.runtime/downloads`。双店异步回归要求两个有销量店铺、完整分页；采购异步回归使用采购页面实际筛选条件，不传店铺 ID，并只覆盖采购可见维度；类目详情会动态选择少于 20000 行的类目样本。缺样本、接口权限不足、超限和任务未完成均不能按通过处理。

采购角色没有店铺权限，因此 CI 不执行依赖两个有销量店铺的异步导出任务；CI 会单独使用采购账号对 SKU、发货仓库、国家、类目维度创建后台任务并核对导出文件。店铺维度不在采购回归范围内。

多个 pytest 进程同时运行时，每个进程必须指定不同且此前不存在的 `--basetemp` 路径（放在 `.runtime/cache/`），避免共享认证状态导致账号串用；不要把其他进程的临时目录作为目标。排序与异步任务耗时较长，应按角色保存各自执行结果。

上述表格记录的是 2026-11-12 尚未加入采购独立异步导出用例时的执行结果；当前 CI 代码已安排采购四个可见维度的异步导出。

主回归、角色回归与排序回归按管理员账号执行非 slow 范围 56 项：2026-11-12 14:17 一次整套执行 55 项通过、1 项按数据不足跳过（组合 SKU 无样本）、10 项 slow 未选。采购与管理员同条件数据一致、受限角色对未授权店铺无可见数据已分别通过。

## 覆盖与限制

| 场景 | 当前自动化 |
|---|---|
| 五维度付款时间查询、时间必填、付款与发货组合、半年边界 | 主回归 |
| SKU、主 SKU、品类、销售状态、短输入和空结果 | 主回归 |
| SKU 创建时间筛选（`createTimeBegin`/`createTimeEnd`） | 主回归，取真实创建日期校验落在窗口内，并验证无数据窗口返回 0 |
| 四维度店铺多选、查询请求及重置 | 主回归，两个有销量店铺 |
| 店铺单选、单个店铺清除、`清除已选` 控件 | 主回归，只从启用店铺取样；UI 选中与取消都核对请求的 `storeIds` |
| 默认供应商筛选（`supplierName`） | 主回归，从最新基线动态取最常见供应商片段；无结果时刷新基线，最多尝试 3 次；核对返回行都包含片段，不跨请求比较 SKU 或总数；另验证无匹配返回 0 |
| 自定义分类筛选（`customClassIds`） | 主回归，从报表数据取真实分类 ID；样本缺失时标记验证不完整并失败 |
| 创建人下拉选项范围与顺序 | 主回归，下拉顺序必须与字典接口顺序一致，并验证停用用户开关存在且不改变首屏选项 |
| 仓库、国家、类目、店铺展开销量 | 主回归，四维度都做 SKU 明细合计对账 |
| 仓库展开的多仓完整性 | 主回归，逐 SKU 核对展开库存合计等于汇总库存，且样本必须存在跨仓 SKU |
| 销量、订单数对销售订单明细；库存对库存 SKU | 主回归；库存接口查不到的 SKU 均列为未核对并使测试失败，不能凭主 SKU 名称推断合并状态 |
| 多店实时及异步文件销量对账 | 主回归，有店铺权限角色的五个维度 |
| 采购异步导出文件销量对账 | slow 角色回归，SKU、发货仓库、国家、类目维度；不传店铺 ID，类目选择小于 20000 行的样本 |
| 导出搜索的内容（`exportOmsInventoryReportV2`） | 主回归，文件行数等于搜索总量，逐 SKU 销量与查询一致，并与当前页导出（50 行）对照 |
| 类目汇总导出（不带 `includeSkuDetail`） | 主回归，单 sheet、行数与类目列表一致，销量/库存/订单数逐行相等 |
| 店铺/仓库/国家明细导出排序 | 主回归，按当前排序列校验导出明细行整体单调 |
| 五角色 Tab 和店铺权限范围 | 角色回归，须用对应账号执行 |
| 采购仓库/国家筛选 | 角色回归，使用采购账号可访问的全店铺范围，不依赖店铺权限列表 |
| 受限角色对管理员可见且有销量的未授权店铺 | slow 角色回归，双账号实时选样并验证四个维度 |
| 采购与管理员数据范围 | slow 角色回归，双账号同条件对账并检查数据是否变化 |
| 角色菜单迁移、创建人下拉 | 角色回归；刷新页面后验证当前字典接口和选项 |
| 无销量但有库存的仓库 | 主回归，需动态找到有效样本并核对汇总库存 |
| 数值排序与当前页文件顺序 | slow 排序回归；SKU 无订单数列 |
| 排序跨页保持、排序传入展开 | 排序回归（非 slow，进 CI），校验翻页请求与展开请求都带当前 `sortField`/`sortOrder` |
| 类目+SKU 明细超过 20000 条 | slow 回归，确认明细超限、直接导出被拒后，同条件创建异步任务并核对文件行数及 SKU 销量 |
| 类目内订单去重 | slow 回归，自动寻找同单同类目多 SKU 样本并与订单源核对 |

尚未实现完整自动化的内容：所有搜索字段的边界组合；组合 SKU 需找到实际订单样本，按当前角色可见范围搜索六个月仍无样本时明确标记验证不完整并失败，不能证明归属正确；2 万条精确边界（只有超过 2 万的数据，19999/20000/20001 无法构造）；采购角色的双店异步文件因无店铺权限不适用。原旧 URL 行为此前明确暂缓。数据不足不等同通过。

采购可查看全部报表数据但不显示店铺 Tab；类目订单汇总按类目内订单去重，不能要求 SKU 明细订单数简单相加等于类目汇总。作废订单在五维度排除；本报表只有销量、订单数、库存三类数值口径，没有退款、退货、售后字段，不存在按退款退货对账的场景。合并 SKU 按业务规则计入报表销量与库存；库存接口查不到时需要其他可靠来源核对，当前自动化不能据此判通过或判报表错误。

组合 SKU 本身不是 SKU 维度的独立统计行；订单已拆分的库存 SKU 明细按各明细数量汇总销量，订单按库存 SKU 去重。组合定义接口可不传 `groupSkuId` 查询，搜索实际订单时优先从可见订单明细定位组合商品，随后查询组合定义；当前组合定义可能与历史订单时点不同，不能据现行定义重算历史销量。无法找到或关联有效明细时，组合场景报告未完成。
