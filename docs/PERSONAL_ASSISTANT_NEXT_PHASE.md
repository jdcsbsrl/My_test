# 个人测试助手下一阶段开发计划

日期：2026-09-07。状态：阶段一、二的有限Mock范围已实现；阶段三待真实需求及人工基线。

## 本轮证据及结论

固定24条虚构订单，覆盖基础查询、订单号精确查询、状态筛选、分页四个场景。
MockKnowledgeAPI替代检索接口，requests.Session.request替代HTTP传输；真实使用生成服务、固定字段策略、AuditAgent、ExcelGenerator、SQLite登记及pytest子进程。
生成4条、登记4条、执行4条通过；固定字段确认0次。目标及相关回归46项通过。
一次完整自动流程耗时6.44秒，仅代表本次机器执行时间，不包含起草、开发、人工审核，不能作为节省工时证据。

故障注入确认：空数据标记验证不完整、业务错误及忽略筛选条件判为失败、缺步骤判为生成错误。
初始反例“精确查询返回所有24条订单”曾被格式审核放行；接入核对后的来源契约后，该反例现被阻断。
这证明有限契约匹配有效，不证明能理解任意自然语言；无契约旧用例明确标记语义未验证。
原文字相似检查会把共享模板的不同场景列为候选；有规则映射后先分组，四场景不再互相提示重复。

## 目标和实施顺序

目标：让一个真实小需求经过审核后可用，并在下一次变化时低成本复用。先补判定依据，再做回归选择，最后验证实际收益。

### 阶段一：业务规则与预期的可核对映射（最高优先级）

实现状态：有限查询契约、来源/版本校验、预期匹配、可执行判断及反例测试已接入。来源文本需事先核对，尚不支持任意自然语言等价判断。

1. 由本地助手从用户需求和KnowledgeRetriever结果提取规则ID、来源版本/摘要、适用条件及可执行判断。
2. 在运行时元数据保存每条用例的规则映射与结构化预期，例如字段、比较操作、期望值、预期条数；正式15列不变。
3. 首批仅支持现有订单查询的精确值、状态一致、数量上下限、分页不重叠；不解释任意自然语言。
4. 校验来源存在、规则引用有效、判断与规则一致及覆盖遗漏。能够确定的矛盾直接阻断；业务知识确实缺失时集中提问。
5. 固定值仍由程序处理。不能把模型生成错误转成用户逐字段确认，也不能把模型自评当作独立正确性证据。

涉及入口：case_generation_service.py、test_case_auditor.py、运行时schema及相关契约测试。
产出：版本化规则映射、有限谓词校验、含来源定位的AuditResult、正常及错误样本集。
验收：正确的4个Mock场景通过；错误精确预期、缺规则、错来源、漏必须场景全部被阻断；无固定字段确认；Excel仍15列。
未知语义必须明确标记未验证，不能因结构审核通过宣称业务正确。

### 阶段二：按变化更新用例和选择回归

实现状态：规则摘要持久化、impact预览、同需求P0补齐、规则分组及新版本历史隔离已完成。当前对象变化通过规则契约object内容摘要反映，尚无独立页面依赖图。

前置条件：阶段一规则映射稳定。

1. 保存用例依赖的业务规则及页面/API对象版本，比较变化后列出受影响用例。
2. 区分内容未变复用、受影响版本更新和明确失效停用；历史及执行证据不删除。
3. 相似提示先按规则和场景分组，再比较正文，降低不同查询场景因模板相同而被提示重复的频率。
4. 输出回归选择原因、关联脚本及相关P0完整性；继续使用现有脚本指纹和失效节点检查。

产出：变化预览、可追溯的版本更新、回归选择报告。
验收：仅修改状态筛选规则时能定位对应场景；基础/精确/分页不会被误停用；相关P0不遗漏；脚本变化后旧PASS不当作新证据。
语义相似只作为建议，不自动删用例。首批验证限定于Mock四场景，不承诺跨全部模块的影响分析。

### 阶段三：真实需求试用与收益验收

前置条件：前两阶段验收通过，并有实际待测需求及可用的测试环境数据。

1. 选择一个真实小需求，由助手检索并起草，人工核对业务规则后执行一遍。
2. 从中选3～5条重复执行价值高的场景关联自动化，沿用已授权范围和环境约束。
3. 在后续一次需求变化中复用，记录实际定位和修复耗时。

记录：人工修改分钟数、业务错误和关键遗漏数、无法执行步骤数、重复提示误报数、失败诊断和修复分钟数。
与相同口径的手工流程比较；没有手工基线就不宣布节省比例。
验收：无未解决关键遗漏，人工总耗时低于基线，所有选定核心场景有可追溯执行证据；达不到则回到最耗时环节修复。

#### 试用执行与记录口径

实际需求尚未提供时，仅准备记录，不将Mock订单场景替代真实需求。首次试用复用现有工具，不新增调度平台或计时服务。

1. 接收需求正文或本地文档路径；助手从中整理需求ID、变更前后行为和验收标准，通过KnowledgeRetriever检索依据。只集中询问缺失或相互矛盾的业务事实，固定字段继续由配置填入。
2. 起草并审核用例，记录业务规则来源、关键遗漏及人工修改。无契约标记“语义未验证”；不能把结构审核通过填成业务已确认。
3. 选择3～5条高复用场景，保存用例ID、版本、脚本节点和执行报告位置。数据不足、跳过和无法执行分别记录，不计为通过。执行沿用既有UAT授权和环境限制。
4. 后续真实变更到来时，先用impact预览并人工核对遗漏，再更新受影响版本；记录定位、修复、复核耗时。没有实际变更就保持“复用待验证”。

每个真实需求的记录保存为workspace日期目录中的独立Markdown交付记录（不是测试用例文件）；测试用例仍用统一Excel导出。敏感内容只保留本地，不放进本计划。

| 记录项 | 填写口径 |
|---|---|
| 需求与范围 | 需求ID、来源位置、验收标准、纳入和排除场景 |
| 依据状态 | 规则来源及版本；已核对、存在歧义或语义未验证 |
| 手工基线 | 相同范围的人工分钟数、测量日期；估计值须注明，缺失留空 |
| 首次人工投入 | 需求整理、业务核对、用例修改、脚本接入、数据准备、诊断修复、结果复核分别计分钟 |
| 机器与等待时间 | 单独记录，不替代人工投入；并行操作不重复累计人工时间 |
| 质量问题 | 业务错误、关键遗漏、无法执行步骤、重复提示误报分别计数，关联处理状态 |
| 执行证据 | 每条用例ID/版本、脚本节点、报告位置、通过/失败/跳过/未执行 |
| 后续变更 | 变更依据、impact选择与实际遗漏、定位/修复/复核分钟数；尚未发生则留空 |
| 验收结论 | 通过、未通过或证据不足，并列出未解决问题 |

首次总人工投入包含脚本接入等一次性成本，后续复用投入另列；不能只选较低的一次报告收益。同口径且基线大于0时，节省比例才计算为（基线分钟数－本次人工总分钟数）/基线分钟数。基线缺失、仅有估计或质量未达标时，只报告观测值，不宣布收益验收通过。

## 本阶段不扩展的范围

暂不开发多Agent调度、通用自然语言转脚本、自动语义去重删除或跨全部模块自动修复。
不以增加用例数量、提高结构分数或Mock通过率作为业务价值指标。

## 可重复执行的Mock入口

在已有测试授权下，使用项目虚拟环境执行：

```text
python -m pytest tests/integration/test_mock_assistant_workflow.py modules/auto_test/tests/test_mock_order_query_contract.py -q
```

运行缓存和中间报告使用.runtime，Mock登记库与日常真实登记库隔离。正式Excel及验收结论保存在workspace日期目录。
