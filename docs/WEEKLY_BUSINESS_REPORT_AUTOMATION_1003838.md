# 业务组周报需求1003838自动化回归

## 执行入口

CI 使用 `modules/auto_test/tests/test_weekly_business_report_1003838.py`。全组金额核对由管理员账号在 TEST 环境执行；业务经理/组长和业务员分别使用独立测试进程、浏览器上下文执行只读权限回归。测试只读当前最新周报，金额来源按每份快照自己的周报截止日查询账单。

本地执行管理员全组核对：

```powershell
$env:TEST_ENV = 'test'
$env:AUTO_TEST_AUTHORIZED = 'true'
$env:WEEKLY_REPORT_ROLE = 'admin'
pytest modules/auto_test/tests/test_weekly_business_report_1003838.py -m 'not slow'
```

全量源账单金额对账属于慢速只读检查，要求周报已按当前 TEST 源数据刷新后再运行：

```powershell
$env:TEST_ENV = 'test'
$env:AUTO_TEST_AUTHORIZED = 'true'
$env:WEEKLY_REPORT_ROLE = 'admin'
pytest modules/auto_test/tests/test_weekly_business_report_1003838.py::test_latest_week_admin_reports_match_source_receivable_bills -m slow
```

GitHub Actions 的 `workflow_dispatch` 可勾选 `run_weekly_report_source_audit` 手动执行同一核对；常规 PR 和每日 CI 不运行这条历史快照与当前账单金额逐笔比对。

## 已覆盖检查

| 需求范围 | 自动化检查 |
|---|---|
| Tab 和搜索 | 六个正式 Tab、无“全部”；五个客户板块均有客户名和客户编号搜索；从可见搜索栏识别普通输入框与自定义下拉控件；检查店长、款期类型、国家搜索控件 |
| 主要客户 | 上周或上上周日均单量至少一周大于 0；按上周日均单量降序 |
| 销量下降 | 上上周大于 0、上周低于上上周、下降比例严格大于 15% |
| 新增与回访判断 | 单元规则验证合作开始日期边界、老客户新店铺条件和上上周回访只看合作开始日期 |
| 付款异常候选账单 | 账单类型 0；状态 0、1、3；应收日期不晚于周报截止日；空应收日期保留；客户编号和客户 ID 与周报行一致 |
| 账单来源核对 | 对最新周报中每组每个付款异常客户读取源账单；同币种客户逐账核对已付未到账、实际未付、应收货款、款期内外、已发货和未发货金额及待付款日期。原始应收、已收、平账字段可用时，实际未付按“应收 - 已收 - 平账”独立重算 |
| 多币种 | 周报同一客户仍为一行；用周报内部金额等式核对；当源账单币种不一致或报表币种不同，不用未经确认的实时汇率伪造金额预期 |
| 配齐比例 | 单元规则区分没有未发货订单（空值）、全缺货（0%）和部分配齐；订单任一明细数量大于锁定库存即视为缺货 |
| 工作计划权限 | 管理员和业务经理/组长可选择多人；业务员只能选择自己 |
| Ctrl+F | 使用周报自带的 Ctrl+F 快捷键和“在全部周报分类中查找”框；从每个有数据的客户板块取一个客户编号，确认命中数大于 0。该用例不宣称逐条覆盖所有周报文本 |
| 数据安全 | 自动化客户端只有查询接口；不更新共享周报、不保存工作计划、不改客户付款信用 |

## 覆盖边界

工作计划、付款信用、数字条件记忆、更新周报、更新付款异常客户信息、保存局部客户集合、日志去重和导出需要写入数据。当前没有发现带本次 `run_id` 所有权、且可由生命周期管理器清理的专用周报/客户夹具，因此 CI 不对共享最新周报发送写请求。金额数字持久化需待项目提供隔离周报数据夹具后，才可以在 TEST 中覆盖“搜索后记忆、重新加载回显”和直接更新落库；在此前用例中只验证控件和访问范围。

新增/回访和配齐比例的业务边界目前由独立规则函数做单元验证；真实周报与源订单的端到端对账、工作计划正文、付款信用更新和日志去重、数字条件记忆、两个更新按钮直接落库、保存不删除未传客户、导出文件名仍需可控测试数据或对应接口契约后再加入端到端验证。不得通过修改最新历史周报或共享客户资料来构造这些用例。

## TEST 接入基线（2026-11-16）

- 管理员最新周报报表周从 `2026-11-02` 开始，先前按账单列表的 `unpaid` 展示值对 11 个业务组、133 条周报客户详情、120 条付款异常客户和 1282 张源账单完成核对（114 条同币种记录逐账核对，6 条跨币种记录只做周报内部等式核对）。改为优先按源账单 `receivableAmount - receivedAmount - balanceAmount` 重算后，当前在业务一组首个付款异常行发现 `receivableAmount` 与周报差异超过 0.02，测试停止；需区分静态快照与源账单后续变化，尚不能判定是刷新时点差异还是计算缺陷。
- 付款异常页要求的金额列和管理员工作计划人员选择检查通过；业务经理工作计划人员选择及客户范围检查已通过。
- 客户名搜索控件当前由自定义下拉组件呈现；旧检查只枚举 `input:visible`，会漏掉下拉控件。已改为检查搜索栏内可见控件标签；TEST 实跑确认五个客户板块都有客户名和客户编号搜索。
- Ctrl+F 旧检查调用 `window.find()` 搜索当前 DOM，没有触发周报自己的快捷键查找，因此曾将未渲染内容误判为缺陷。TEST 浏览器实测按 Ctrl+F 后出现“在全部周报分类中查找”框，搜索一个付款异常客户名显示 `1/3` 并定位到其他板块。自动化已改为通过真实快捷键和查找框抽查各有数据板块的客户编号，TEST 管理员实跑通过；该检查不代表逐条覆盖所有报告文本。
- 销售员角色需 CI 提供独立账号凭证后执行；本地没有配置该账号，尚未完成销售员现场回归。

修正前两项检查的失败不能作为 TEST 功能缺陷结论；以修正后的 UI 回归实跑结果为准。

实际未付和发货金额不加统一的非负断言：历史应收金额调整可能使“应收 - 已收 - 平账”为负，周报会按原始发货比例分摊这个负数。回归验证源公式和拆分等式，避免把账单列表展示层的非负截断误当成周报口径。
